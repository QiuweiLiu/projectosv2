# L0 + L1 验收记录（2026-11-04）

范围：**客户端与后台服务解耦**（L0）与**读写 API**（L1）。
不含 L2 界面；`--control` 页面仍是只读看板 + 目标输入框。

## 1. 做了什么

| 项 | 内容 |
|---|---|
| 后台服务 | `serve --daemon / --stop / --status`；`serve.json`（pid/addr/control/started）；`serve.log` |
| 脱离会话 | 子进程 `Setsid` + **文件日志**（不是管道）；`--stop` 只停 HTTP，不杀在跑的任务 |
| token | 存 `control-token`（0600），重启后不变 |
| 读 API | `/api/objectives`、`/api/objectives/{id}`、`/api/events?after=` → `{events,next}` |
| 写 API | `confirm` / `run` / `cancel`，全部转成 `kernel goal ...` 子进程 |
| 取消 | `kernel goal cancel`：flag 文件 + 持有状态目录的 scheduler 消费 |
| 单写者 | `store.Open` 打开即取得 `kernel.lock`；读命令改只读打开 |


结论：关闭/杀死客户端不中断已托管任务，交付照常生成。

### B. 运行中取消

```
setup l0b: DIR=/private/tmp/l0b-102941 id=obj-1793759381
running after 2 polls
cancel requested; the running scheduler will stop
cancelled after 7 checks           ← ~14s（轮询周期 3s）
objective=obj-1793759381 status=cancelled
E1   blocked  attempts=1 cancelled: user pressed cancel
残留 goal run 进程: 0
```

结论：取消在一个轮询周期内生效，Abort 会取消 AO 会话，不留孤儿。

## 3. 顺带修复的真实缺陷

`store.Open` 每次打开都会执行恢复（running Run → unknown，running Task → blocked）。
也就是说**在任务运行时执行一次 `kernel goal status`，会把正在跑的任务判死**。

修复：

- `store.Open` 在打开数据库的同时取得 `kernel.lock`，恢复只属于写者；
- 读命令（`status/show/export/resume/serve`）改用 `OpenReadOnly`，不触发恢复；
- 回归测试：`TestOpenOwnsStateDir`、`TestReadOnlyOpenDoesNotRecover`。

同类问题：`serve --daemon` 的 `goal run` 子进程原来用管道收集输出，父进程一死子进程会
收到 SIGPIPE。改为写文件日志。
