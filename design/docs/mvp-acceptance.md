# ProjectOS 2.0 — 首个 MVP 验收规格

状态：供用户审阅的首阶段规格；已获准编写与源码核验，尚未获准业务实现或真实 Agent 运行。
日期：2026-11-02（Asia/Shanghai）。依据：用户背景、当前任务授权及 upstream-capabilities.md。

## 1. 目标与边界
证明一个已授权目标可被系统持久化为两个依赖任务，由一个真实 Worker 顺序执行，以固定版本的产物和独立检查判定验收，正确推进依赖，并在中断后核对恢复。

首版范围：单机、单用户、一个 Objective、A → B 固定依赖、一种 Harness、一个 Chat Worker Session；每个任务拥有独立 Run，关联同一 Session 的不同 turn。执行与验证串行。不开启上游项目协调 Agent 自主派发，ProjectOS 是业务任务唯一调度者，Orchestrator 是 Session/进程唯一生命周期所有者。

首版以最小命令入口与可读状态满足验收；完整桌面交互、多 Worker 并行、自动 LLM 规划、插件市场和通用能力包加载均留待后续。这里是产品增量范围，不改变长期愿景。

## 2. 一个具体、低成本的场景
在专用、可丢弃的测试工作区实现“整数求和”工具，禁止操作现有业务项目。Python 标准库只是验收样例的候选，不决定 Kernel 的实现语言；真实运行前核验本机解释器并记录版本。

| 单元 | 输入与任务 | 产物 | 确定性验收 |
|---|---|---|---|
| A | 已批准的函数契约：sum_integers(values)，values 为整数列表，空列表返回 0 | 独立模块 sum_integers.py | 外部验收用例：[]→0；[1,2,3]→6；[-3,1]→-2；[0]→0 |
| B（依赖 A） | A 已验收的产物版本；实现调用 A 的 CLI | sum_cli.py 与使用说明 | 运行 sum_cli.py 1 -2 3，退出 0、stdout 为 2 加换行；无参数输出 0 加换行；非法整数退出 2、stderr 非空；重新运行 A 的全部用例 |

B 必须实际复用 A 的函数。B 后的整合版本需再次验证 A，不能凭 A 的旧验收替 B 背书。若 B 合理修改 A，创建新的产物版本，重新核验组合，不覆盖 A 的历史证据。

验收用例和检查入口由可信控制方保存于 Worker 写入范围之外；不能让 Worker 修改测试或仅提交“测试已通过”的文字。验证须运行冻结产物，记录命令、解释器、cwd、退出码与输出，并检查应有用例数量；测试文件被改、跳过或不存在均不通过。

## 3. 最小业务记录与写入责任
具体字段类型、数据库 schema、API 尚未冻结；下列为行为所需记录，不是新增上游接口。

- Objective：目标、范围、授权操作、成功条件、预算、状态。
- Task：ID、依赖、输入产物版本、验收条件版本、当前状态。
- Run：ID、Task ID、attempt、发送标识、Session ID、turn ID、起止与执行结果；重试新增 Run，不覆盖旧记录。
- Artifact：可恢复快照位置、内容标识及归属 Run；仅有文件路径不足以绑定版本。
- Verification/Review：目标 Artifact 版本、检查规则版本、结果和证据位置；缺失/不匹配的证据不能验收。
- Approval：批准的具体操作、范围及版本。执行器内部工具审批与 ProjectOS 任务授权分别处理。

ProjectOS 独占 Task/Run/验收及依赖更新；Orchestrator 独占 Session/进程操作。Worker 仅提交产物与执行结果。项目长期摘要在 .project/，未来运行态使用一个明确的事务存储；两者不维护互相竞争的任务事实。第一版不依赖多写者或双写同步。

## 4. 任务推进与产物冻结
A READY，B PENDING → A RUNNING → VERIFYING → 按风险必要时 REVIEWING → A ACCEPTED → B READY → 同样流程验收 B → Objective 完成。

- 业务 ACCEPTED 由控制方在证据与产物版本匹配时写入；Session idle/exited、HTTP 201/202、模型自报完成均不能触发。
- A 的验收写入与 B 的就绪更新必须原子化，或以持久事实确定性推导，保证重启不漏推进、不重复推进。
- 每个任务发送前先持久化 Run 和稳定投递键；重复发送沿用该键和原始 payload。新 attempt 才使用新键。
- A 完成主 turn 后，确认没有活动/排队的写入 turn，采集冻结快照；验证期间不派发 B，不开放并发文件写入。无法确认静止就 BLOCKED；快照有变化就重新采集和验证，旧证据不能验收新内容。
- A 验收后在同一 Session 发送 B，以复用工作区；A 的冻结快照和验证证据保留。Session/native conversation 的恢复能力需要下一阶段真实核验。
- 无法可靠把发送标识映射到特定 turn/Run 时 BLOCKED，不猜测最近一条消息。
- 验证不通过：保留失败 Run 和输出，A 进入 FAILED，B 保持 PENDING；无自动循环修复。用户明确重试后追加新 attempt。
- 审批等待 WAITING_APPROVAL；暂停与取消意图必须先持久化，再执行停止派发或请求中断。恢复时先读取该意图：暂停后即使 Task READY 也不能派发，直到用户明确恢复；取消后 CANCELLED 并停止后续派发。仅在确认旧执行已停止后才允许重试；停止状态不明则 BLOCKED。恢复取消流程时继续核对原 Session，而非丢弃关联后重建 Worker。

## 5. 可判定验收清单
以下均为未来必须执行的测试，本阶段没有运行结果。

| ID | 操作/故障注入 | 通过条件 |
|---|---|---|
| M01 正常闭环 | 真实 Worker 完成 A，再完成 B | A 证据匹配后才发送 B；同一时刻仅一个业务 Run 写入；B 全部检查通过后 Objective 才完成 |
| M02 假完成 | Worker 报告成功但函数对负数给错结果，或测试缺失 | A 不 ACCEPTED；保存失败证据；B 没有发送记录 |
| M03 前置未验收 | A turn 已结束但验证尚未完成，反复触发调度 | B 保持 PENDING，无第二条业务 turn；HTTP 成功不能绕过依赖 |
| M04 验收边界恢复 | 在 A 验证完成但业务提交前、提交后但发 B 前分别停止 ProjectOS 再启动 | 前者重新确认同版本证据并提交；后者读取 ACCEPTED 只派发一次 B；不覆盖旧 Run |
| M05 投递不确定 | A/B 消息已被 daemon 接受，但响应丢失；或投递途中服务重启 | 沿用原投递键核对持久会话与 turn，不生成新键盲重发；已确认记录不重复执行。无法判定则 BLOCKED 且 B 不推进，不能假称 exactly-once |
| M06 生命周期恢复 | 分别关闭/重开展示界面、重启 ProjectOS；另测 daemon 重启与 Harness 断线 | 前两项恢复已持久化任务且不重复创建 Worker；后两项先核对 Session/native checkpoint。可恢复则继续原 Run，证据不足则明确 BLOCKED，不把断线当失败后立即重跑 |
| M07 版本绑定 | A 验收后篡改工作文件，或在验证时继续写入 | 不把旧 Evidence 用于新内容；阻止派发或重新冻结验证；B 最终必须回归测试 A |
| M08 人工控制 | 运行时暂停、取消；在写入控制意图后重启 ProjectOS；模拟权限请求与预算耗尽 | 暂停停止新派发（当前 Run 继续被观察），重启后仍暂停，明确恢复后才派发；取消请求通过 daemon 发出并在重启后继续核对；确认停止前不重试；权限待批准时不代答；预算到限停止新派发并请求人工处理 |
| M09 并发和迟到结果 | 两次同时触发“继续”，或旧 attempt 完成消息晚到 | 只有一个有效 Run 被派发；旧结果保留但不能覆盖当前 attempt 的状态或验收 |

M05/M06 不确定时安全阻塞是正确行为，但只有此结果不足以宣称“自动恢复已通过”；必须在报告中区分“成功恢复路径”与“安全阻塞路径”。自动恢复子目标需真实成功案例。

## 6. 预算与审查
候选运行约束：业务 Worker 并发 1；每 Task 初始 1 次 attempt，失败后仅人工批准重试；单次执行最长 10 分钟，单次本地验证最长 60 秒。正式数值在真实运行前由用户确认，并记录实际 Harness/模型；本轮不消费外部模型额度。

墙钟/运行次数可由程序确定性限制；Token/金额只有执行器可靠提供时才统计/限额，不把估算写成实际账单。到限先停止新派发，对进行中的操作请求停止并核对。

小样例优先确定性验收；独立审查用于关键实现/最终闭环，至多一次完整审查和一次阻断缺陷定向复审，绑定产物版本。Reviewer 不可直接更改 Task 为 ACCEPTED。无 PR 的本地审查不能默认使用上游 PR 审查接口替代。

## 7. 验收记录与下一阶段
未来每个 Mxx 保存操作顺序、固定版本、输入、预期/实际状态、Run/turn 关联、产物版本和输出证据；放在项目约定的测试/运行记录位置，摘要引用它们。不存在证据的项目记为未测。

下一阶段建议是最小接口可行性验证：先确认一款 Harness 的 Chat 模式、稳定键投递、快照/主 turn 完成识别、工作区产物读取和 daemon 重启行为；再决定集成路线并实现最小控制逻辑。真实运行、依赖安装和代码修改均需新的明确范围授权。
